| 项 | 改前 | **改后** |

**代价（如实登记，不藏）**：1500 < 1600、3000 < 3330 ⇒ **给用户的额度更少 ⇒ 运营方毛利更高 ⇒ 少让利 1.7 / 2.8 个点**。

**收益**：pro 的年付守线余量从 **0 个点**变成 **9.75 个点**（旧值 3330 在旧年付价 ¥999 下正好压在 40.0% ⇒ 年付价一降就破线）。

## 1. 为什么改（三条根因）

### 1.1 根因一：旧值 3330 是「唯一交点」，年付守线余量为 0

旧赠送量 3330 满足两个式子同时成立：`0.01M / 119 = 28.0%`（月付目标占比）且 `12 × 0.01M / 999 = 40.0%`（年付守线）。
⇒ **它不是「选得不好」，是「被两个式子夹出来的唯一解」** ⇒ **年付守线余量必然是 0** ⇒
年付价只要往下动一档（做活动年付），**立刻破守线**。

### 1.2 根因二：唯一交点会随价格漂移，不能当长期口径

「月付占比 = 目标占比」是**运营目标**（随商业决策变）⇒ 用它当硬口径 ⇒ 每次改价都要重解一次，且解出来的数**必然贴线**。

### 1.3 根因三：对外宣传数字是碎的

H3 768P 10 秒 = 500 积分 ⇒ 1600 ÷ 500 = **3.2 条**、3330 ÷ 500 = **6.66 条** ⇒
宣传页只能写「约 3 条」⇒ **宣传值要么向上取整（超出实际 ⇒ 变相超卖），要么写小数（不专业）**。

⇒ 本次改用**「两条守线 + 体感整除」**作为口径，放弃「唯一交点」。

## 2. 定价口径（真源与推导）

### 2.1 唯一真源与派生

```
唯一真源：packages/api-publish-engine/src/auth/plan-matrix.js
  ├─ priceMonthlyCents   : 5900 / 11900      （月付价，分）
  ├─ priceYearlyCents    : 59000 / 119000    （年付价 = 月付 × 10，分）
  └─ officialCreditMonthly: 1500 / 3000      （官方积分额度，唯一额度字段）

派生（不得各写一份）：
  年付发放量   = officialCreditMonthly × 12      ⇒ 18000 / 36000
  月付成本     = officialCreditMonthly × ¥0.01   ⇒ ¥15 / ¥30
  月付成本占比 = 月付成本 / priceMonthly          ⇒ 25.42% / 25.21%
  年付成本占比 = 年付成本 / priceYearly          ⇒ 30.51% / 30.25%
  年付折扣     = 1 − (年付价 ÷ (月付价 × 12))    ⇒ 16.7%（两档同值）
```

⚠ **`officialCreditMonthly` 是唯一的官方积分额度字段**（不设年付专用字段）⇒
年付按月等额发放即自动满足「年付 = 月付 × 12」⇒ **改赠送量时年付量自动跟随，不需第二处同步**。

### 2.2 两条守线（判定规则）

| 守线 | 公式 | standard | pro | 余量 |
|---|---|---|---|---|
| 月付守线 | `0.01M / 月付价 ≤ 30%` | 25.42% | 25.21% | 4.58 / 4.79 个点 |
| 年付守线 | `12 × 0.01M / 年付价 ≤ 40%` | 30.51% | 30.25% | 9.49 / 9.75 个点 |

⇒ **守线是「不越界」，不是「恰好等于」** ⇒ 与「唯一交点」的本质区别。

### 2.3 体感整除（选 1500 / 3000 的第二个理由）

H3 官方价（`MiniMax 中国开放平台` 2026-10-25 抓取）：

| 规格 | 官方价 | 积分/秒 | 10 秒成本 |
|---|---|---|---|
| H3 2K | ¥0.80/秒 | 80 | **800** |
| H3 768P | ¥0.50/秒 | 50 | **500** |
| H3-Highspeed 768P | ¥0.40/秒 | 40 | 400 |
| H3-Lite 768P | ¥0.26/秒 | 26 | 260 |
| H3-Lite 480P | ¥0.16/秒 | 16 | 160 |
| image-01 出图 | ¥0.025/张 | — | **2.5 / 张** |

⇒ **1500 ÷ 500 = 3 个整**、**3000 ÷ 500 = 6 个整**
⇒ 对外话术可直接写「标准版每月 **3** 条 10 秒 768P 视频」「专业版每月 **6** 条」⇒ 不用出现 3.2 / 6.66。

## 3. 数据校验（口径落库前必须过的检查）

| # | 校验项 | 判据 | 失败后果 |
|---|---|---|---|
| V1 | 赠送量为正整数 | `officialCreditMonthly` ∈ ℕ⁺ | 额度语义崩（0 = 无额度） |
| V2 | 月付守线 | `0.01M / 月付价 ≤ 30%` | 毛利被击穿 |
| V3 | 年付守线 | `12 × 0.01M / 年付价 ≤ 40%` | 年付超卖 |
| V4 | 年付价 = 月付 × 10 | `priceYearlyCents == priceMonthlyCents × 10` | 折扣口径漂移、对外话术不一致 |
| V5 | 年付发放量 = 月付 × 12 | 派生（唯一额度字段 ⇒ 自动成立） | 与「年付 = 12 个月权益」不符 |
| V6 | 相邻档倍率 | `pro价 / standard价`（月付 2.02×、年付 2.017×）落在 1.8–2.2× | 档位梯度失衡 |
| V7 | `PLAN_MATRIX_VERSION` 与改动同步 | 版本串 = 改动日期 | 下游按版本做缓存/兼容判断时读到旧值 |
| V8 | 契约测试逐值一致 | `plan-matrix.test.js` 断言 30/1500/3000 + 守线 | **不同步改 ⇒ CI 当场红** |
| V9 | 宣传数字整除 | `floor(M ÷ 单次成本 × 0.8)`，且宣传值 **≤** 实际值 | 宣传 > 实际 ⇒ 变相超卖 |
| V10 | 官方成本不为 0 也不被高估 | 价格卡单价 = 官方挂牌价换算的微元数 | 「把官方价格低」⇒ 长期亏损 |

⚠ **V10 的具体口径**：`unit_price_micros` 记 **官方成本**，**不记**「我们收多少」
⇒ 成本账（价格卡）与售价账（扣分取整）**分离** ⇒ 官方价变更只需改价格卡新行（`effective_from`），不影响扣分逻辑。

⚠ **④⑤⑥ 的顺序不可颠倒**：文档是口径的对外载体 ⇒ 先改真源，再改派生，最后标历史失效
⇒ 否则会出现「marketing 已改、真源未改」的短暂不一致（评审会当场问）。

### 4.2 用户侧的额度与扣减流程（语义改造，本期不实现）

```
发放（当前）：月付发放 officialCreditMonthly 积分，当作「可发上限」
  ↓ 待改
发放（目标）：月付发放 officialCreditMonthly 积分，作为「发放量」；
             扣减时按**实际消耗**从发放批次里扣（余额可为 0 但批次已发）

扣减：ceil(实际成本微元 / 10000) 积分
     实际成本 = 单价卡 × 实际用量（时长 / 张数 / 字符数）
```

⚠ **本 PR 只改「发放量」与「年付定价」两个口径**；**发放量语义从「上限」变「发放量」+ 实际扣减接线属于官方算力接线第 5 轮**，不在本 PR 范围。

## 5. 功能逻辑

### 5.1 `officialCreditMonthly` 的三种读法（必须区分）

| 读法 | 场景 | 正确值 |
|---|---|---|
| **额度上限** | 权益页「每月最多可生成 X」 | `officialCreditMonthly` ✅（本期维持） |
| **发放量** | 周期开始时发到余额 | `officialCreditMonthly`（**待接线**） |
| **成本换算** | 扣分时算消耗 | `ceil(实际成本 / 1 积分)`，**不是**额度字段 ⚠ |

⚠ **第三种最危险**：把 `officialCreditMonthly` 当成「每单位成本」用 ⇒ 成本与真实价格脱钩 ⇒ 亏本。

### 5.2 扣分取整的落点

```
成本（微元，整数） ──÷ 10000（微元/积分）──► 积分（可为小数）──ceil──► 实扣积分（整数）
                                                            ▲
                                    ★ 取整只发生在这里，且只向上
```

⚠ **单张出图的特例**：`image-01` = 2.5 积分/张（**亚积分**）
- 一次请求 N 张 ⇒ 实扣 `ceil(2.5N)`：N=2 ⇒ 5（精确）、N=10 ⇒ 25（精确）、N=1 ⇒ 3（**多 0.5**）
- ⇒ **实扣永远 ≥ 官方成本** ⇒ **不存在「把官方价格低」的风险** ✅
- ⇒ 取整粒度必须落在**扣分侧**；价格卡里记的仍是官方成本 25000 微元/张
- ⚠ **宣传数字按「一次请求累计」算**（一次 10 张 = 25 积分），**不按每张 3 积分算** ⇒
  ⇒ 对外「每月约 30 张」是按 2.5 积分/张 的 0.8 安全垫算的（1500 ÷ 2.5 × 0.8 = 480 张）
  ⚠ 若改按 3 积分/张算会变成 400 张 ⇒ 两个口径不一致 ⇒ **以「官方成本口径」为准，并在文案里不承诺张数精度**。

### 5.3 降级到更贵模型时的扣费（U-18 = B）

- 系统自动切换模型时，**按实际使用模型的官方价扣**，不按原计划模型
- ⇒ 用户被多扣 ⇒ **界面必须如实说明**
- ⚠ 触达文本见 §7.3

## 6. 交互逻辑

### 6.1 权益页 / 会员中心

| 位置 | 交互 | 数据来源 | 边界 |
|---|---|---|---|
| 档位卡「官方积分」 | 显示 `officialCreditMonthly` 积分/月 + 「约 N 条 10 秒 768P」 | `plan-matrix.js` + 价格卡 | 余额为 0 时显示「0」，**不显示**「—」（0 是有效值） |
| 年付说明 | 「年付 = 10 个月价格，全年 12 个月权益」 | 派生 | 不得再写「便宜 29.5%」 |
| 余额区 | 显示已用 / 剩余 | 账本 | 「已用」为 0 时显示 0 |
| 额度不足时 | 拦截 + 提示剩余缺口 | 账本 | **不得**自动降规格绕过额度 |

### 6.2 生成前预检（官方算力接线第 5 轮实现，本期只定口径）

```
用户点生成
  ↓
按「计划模型 + 计划规格 + 计划时长」估算积分（价格卡 × 预估用量）
  ↓
剩余 < 估算 ⇒ 拦截，提示「还差 X 积分」（见 §7.2）
  ↓
足够 ⇒ 放行 ⇒ 实际消耗按官方响应里的 usage 结算（可能 > 估算 ⇒ 走欠款，见下）
```

⚠ **预检是 UX 快速失败，不是资损防线** ⇒ 真正防资损靠「扣分时余额足够才发货」。

### 6.3 欠款（U-17 = A 的当前形态 + 预留）

- **当前形态（本期）**：余额不足 ⇒ **直接拦截，不发货**（无欠款）
- **预留**：账本加 `debt` 字段（加列安全方向），余额允许为负的形态**本期不启用**
- ⇒ 以后若要放宽到「允许小额透支」，**不需要再改表结构**

## 9. 遗留与诚实边界

1. **发放量语义未改**：当前仍是「可发上限」⇒ 语义改造 + 实际扣减接线在**官方算力接线第 5 轮**。
2. **用量侧维度未补**：`model_usage_daily` / `model_usage_events` 仍**没有** `model` / `spec` / `duration` / `item_count` ⇒
   ⇒ **按模型+分辨率计价现在还做不到**（回算仍按 `(provider, action)` 命中通用卡）⇒
   ⇒ **H3 价格卡在回算链路改造完成前不能入库**（否则多张卡互相覆盖 ⇒ 静默用错规格的价）。
3. **H3 尚未接入**：preset/adapter 只有 `MiniMax-Hailuo-2.3` / `MiniMax-Hailuo-02` / `T2V-01` / `I2V-01`；
   H3 走**新的 V2 端点**（`POST /v2/video_generation`、请求体是 `content` 数组、中国站 `api.minimax.cn`）⇒ 属第 5 轮。
4. **H3-Max / H3-Max-Turbo 暂不建卡**：官方定价页与 V2 接口文档对这两个型号的描述**互斥**
   （V2 文档的 model 列表**没有 Max-Turbo**，且把「极速生成」给了 H3-Max）⇒ 待实测确认后再建。
