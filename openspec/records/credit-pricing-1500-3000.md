## learnings

### lesson: 把「唯一交点」当硬口径，守线余量必然是 0

**现场**：旧赠送量 3330 满足两个式子同时成立 —— `0.01M/119 = 28%`（月付目标占比）且
`12×0.01M/999 = 40.0%`（年付守线）。它是"被夹出来的唯一解"，**不是选得不好**。
⇒ 它的年付守线余量**必然是 0** ⇒ 年付价只要往下动一档（做活动年付）**立刻破线**。
而仓内的守线断言只判"越界"（`≤ 40%`），**不判"贴线"** ⇒ 3330 稳稳通过 ⇒ **逃逸了几个月没被发现**。

**根因**：把「运营目标等式」当成了「安全约束」。目标是会随商业决策漂移的量，用它定死额度 ⇒
解出来的数必然贴着另一条约束；**安全约束应当是"不越界"，不是"恰好等于"**。

**可复用的 N 条**：

1. **凡是用两个等式解出来的"唯一值"当长期口径，先算它离另一条约束有多远** ⇒ 余量为 0 的值是**定时炸弹**，不是最优解。
2. **判据要卡"贴线"，不能只卡"越界"**：守线类断言最好再加一条**余量下限**（本轮：年付余量 ≥ 9 个点）。
3. **"目标"与"约束"要分开写进文档**：`目标占比`是商业决策（可调），`守线 ≤ 40%`是安全约束（不可越）⇒
   混成一句"唯一交点"就会让两者互相绑架。
4. **体感的"整除"也能当口径**：1500 ÷ 500 = 3、3000 ÷ 500 = 6 ⇒ 对外承诺是整数；
   旧值除不尽（3.2 / 6.66）⇒ 宣传值只能写"约"或向上取整（变相超卖）⇒ **"凑整"不是美观问题，是承诺可兑现性问题**。

### lesson: `git diff origin/main HEAD` 在 base 落后时**不是 PR 差量**（会把别人的新提交算成你的删除）

**现场**：为确认"main 新合入的 #4450 有没有碰我改的文件"，我用了
`git diff --name-only origin/main HEAD` 与 `git diff --name-only <我的base> <新main>` 求交集
⇒ 交集**非空**，且包含 **#4450 的 95 个文件**（`CreateView.vue`、`member-center` 前端、
`provider-saturation.js`、`collector-contract.js` …）⇒ 看起来像"我的 PR 会把别人的改动全还原掉"。

**根因**：⚠ **base 落后时，`origin/main → HEAD` 的方向是"新 main 减去我的分支"**
⇒ main 上**新进**的内容在我的 HEAD 里没有 ⇒ 全部被算成**我的删除**。
⇒ 真实 PR 差量的基准是 **merge-base(base, head)**（GitHub PR 页面也是这个口径），
不是「当前 main 的 tip」。

**可复用的 N 条**：

1. **算 PR 差量一律用 `git diff $(git merge-base origin/main HEAD) HEAD`**
   ⇒ 方向是「我的 base → 我的 head」⇒ 只含我的改动。
2. **⚠ 数字可能"看起来对"而口径是错的**：本例两个口径的**增删总数恰好相同**（#4450 的正负抵消化），
   只有**文件数**暴露了问题（17 → 112）⇒ ⇒ **别只看总数，要看文件数与文件身份**。
3. **"我的 PR 会还原别人的改动"这个结论，必须用 merge-base 口径下的重叠文件来判**，
   不能用 `origin/main HEAD` 的交集 ⇒ 否则会得出"必须 rebase"的**假紧急结论**，
   白白多跑一轮 CI（仓内 `strict:false` 本来就不需要）。
4. 同族既有教训：「**基线取 merge-base，不是 base 分支当前 HEAD**」—— 本条是它在
   **本地自算差量**时的同型陷阱（既有教训多在门禁脚本口径，本条在人工取证口径）。

### lesson: 回读校验「旧串 0 残留」在「新串设计上包含旧串」时必然误报

**现场**：本轮 41 处替换里有 2 处「失败」—— 回读说"仍有旧串残留"。
实际是**新串本身就把旧串包在里面**（① 给历史段落前面加失效横幅，正文原样保留；② 在旧注记前加新版注记，旧注记整段保留）⇒
⇒ 这 2 处替换**实际是成功的**，是我的校验逻辑（`if old in content: fail`）与设计冲突。

**根因**：把「旧串 0 残留」当成了绝对判据，但**"保留历史 + 前置新说明"是合法的编辑形态** ⇒
旧串**应该**留在那里。此时"残留"与"刻意保留"在字节层面**无法区分**。

**可复用的 N 条**：

1. **回读校验要写成"旧串出现次数 == 预期次数"，不是"== 0"** ⇒ 预期次数按编辑意图给（保留历史 ⇒ 1；彻底替换 ⇒ 0）。
2. **"新串包含旧串"时要显式声明意图**，否则失败报告会指向错误的行，浪费一轮排查。
3. 同族：**"回读一致"只证明传输无损**（既有教训）—— 本条补的是**"回读失败"也可能是判据自身有缺陷**，⇒
   **失败信息本身要当线索查，不要当结论**。

### lesson: 改真源 ⇒ 必须按**字段名**全仓搜下游引用点（一次 CI 红只证明第一个坏点）

**现场**：把年付价从 ¥999 改成 ¥1190（改 `plan-matrix.js` 这一个真源）⇒ CI 首轮在 `QG Unit Tests` 红了
⇒ 红的是 `subscription-payment.test.js` 断言 `99900`。但**顺着"报红的那一处"只改它**⇒ 会漏掉另外两处：
桌面端 `Subscription.test.js` 的 fixture（49900/99900）与 `OrdersBilling.test.js` 的 fixture **+ 硬断言 `'¥999.00'`**。

**根因（两条）**：
1. **真源与断言之间是多对多的**：一个字段被 N 处引用，其中**只有一部分是硬断言**、其余是 fixture。
   fixture 不红 ⇒ **它在替你把旧口径藏着**。
2. ⚠ **CI 的 direct 阶段"一个文件一个进程、失败即退"** ⇒ 一轮 CI **只报第一个坏点**
   ⇒ 绿的那 20 个文件**不构成"其它都没问题"的证据**（尤其在**失败点之前**的文件根本没跑）。

**可复用的 N 条**：
1. **改真源 ⇒ 按"真源字段名"搜引用面，不是按"旧值"搜**（搜字段名能找到读该字段的全部消费者，含不硬编码旧值的那些）。
2. **区分"硬断言"与"fixture"**：fixture 要**一并对齐**（否则它继续掩盖漂移），但它不红 ⇒ 不能靠 CI 发现。
3. ⚠ **弱断言要专门查**：`toContain('¥59')` 对 `'¥590'` 成立 ⇒ **前缀型金额断言无区分力** ⇒
   金额类断言要写**完整值**（`¥590` / `¥1190`），否则改了价照样绿。
4. **首轮红的正确读法**：它标出**第一个**坏点，**不是**坏点全集 ⇒ 修完必须**再按字段名搜一遍**才能下"没有别的了"的结论。
5. ⚠ **否定式取证要有 exit code 兜底**：一次 `grep` **静默超时**在本轮真的发生过 ⇒ 它会被读成"零残留"
   ⇒ 逐目录 grep **必须校验 exit code**（`124` = 不可判定，不能算"无残留"）。
