## 〇、一句话

把「这笔该不该扣、能不能扣、扣不成功怎么办」变成**可机械判定的状态机**，
并把一条**安全红线**钉进代码：**客户端上报的用户身份不可信 ⇒ 客户端事件永远不进扣分队列**。

---

## 一、为什么这一刀不是「把扣分接上就行」

### 1.1 一条必须先说清的事实：**客户端上报的身份不可信**

`POST /api/v1/usage/events` 的鉴权是 `require_catalog_key`（静态 `X-Catalog-Key`），
**请求里没有任何用户身份** ⇒ 事件体里的 `user_id` 是**客户端自称**的。

⚠ 若直接拿它去扣分 ⇒ 恶意客户端上报**别人的 sub** ⇒ **扣别人的积分**。
⇒ 这不是「将来收紧」的问题，是**现在就不能这么写**。

### 1.2 根子上：当前形态下**客户端直连 = BYOK**

桌面端直连 provider 时用的是**用户自己配的 Key** ⇒ 那条路上的调用本质是 BYOK
⇒ **官方算力不担成本 ⇒ 本就不该扣官方积分**。

⇒ 真正的官方算力（扣官方积分）只能发生在两条路上：
- **ops-center 代理上游**（D-①，已定案根决策）⇒ 身份已认证；
- **客户端持平台签名凭证**（尚未落地）⇒ 身份可验证。

⇒ **结论：扣分的数据面现在就能铺，但「可扣的对象」要等这两条路之一落地。**

### 1.3 所以这一刀**不写**补扣执行体

补扣执行体 = 读 `pending` 事件 → 调扣分端点。现在 `pending` 恒为空 ⇒ **写出来是恒空转的死代码**。
⇒ 这一刀只做**数据面 + 判定 + 安全红线 + 结论显性化** ⇒ 执行体留到有流量时再写（宿主选型 U-14 也一并留到那时）。

## 二、扣分状态机

### 2.1 五个状态（**每个含义单一，不合并**）

| 状态 | 含义 | 会不会去扣 |
|---|---|---|
| `not_applicable` | BYOK：用户自带 Key，官方算力不担成本 | ❌ |
| `free` | 成本为 0（上游免费） | ❌（engine 也会拒 `costCents=0`） |
| `unbillable` | **不该扣但有原因**（缺价 / 无用户 / 身份不可信） | ❌ |
| `pending` | 已算好成本与积分，等扣 | ✅ |
| `settled` | 扣分成功（账本已记） | 已扣完 |

⚠ **`not_applicable` / `free` / `unbillable` 三者虽然都「不扣」，但语义不同**
（钱由用户出 / 上游没收钱 / 算不出来）⇒ **共用一个标记会让统计与对拍分不清** ⇒ 必须分旗。

⚠ **`unbillable` 的具体原因放 `charge_error`**（`MISSING_PRICE` / `MISSING_USER` / `UNTRUSTED_IDENTITY`）
⇒ 状态是「不该扣」这一个意思，原因码负责细分。

### 2.2 判定顺序（每一步排除更根本的原因）

```
① BYOK              → not_applicable
② 缺价（算不出成本） → unbillable / MISSING_PRICE
③ 无用户            → unbillable / MISSING_USER
④ 成本为 0          → free
⑤ 来源不可信        → unbillable / UNTRUSTED_IDENTITY   ← ★安全红线
⑥ 其余              → pending
```

⚠ 判定是**纯函数** `resolve_charge_state()`（无 IO）⇒
客户端入口与将来的代理入口**共用同一份** ⇒ 不会出现「两处实现漂移」。

### 2.3 来源标记（`charge_source`）

| 值 | 含义 | 可否扣 |
|---|---|---|
| `client` | 客户端上报（身份不可信） | ❌ **永不** |
| `server` | ops-center 自己写（代理上游，身份已认证） | ✅ |

⚠ **缺省必须是 `client`**（安全侧）⇒ 忘写来源时落到「不扣」而不是「扣」。

### 2.4 周期在**事件发生时**算好并落库

`charge_period_start` / `charge_period_end` = 事件发生时的**自然月边界（UTC）**
（与 `identity_entitlement_usage` 同期口径）。

⚠ 为什么不留到扣分时再算：**补扣可能跨月** ⇒ 那时算出来的周期会与「额度所属周期」错位
⇒ 周期必须**随事件一起定下来**。

## 三、数据面（`model_usage_events` 补 11 列）

| 列 | 类型 | 用途 |
|---|---|---|
| `duration_seconds` / `item_count` / `char_count` | INTEGER | 三个用量维度（R5-1 已加，本刀沿用） |
| `charge_status` | VARCHAR | 五个状态取值 |
| `charge_source` | VARCHAR | `client` / `server`（**安全边界**，缺省 client） |
| `charge_period_start` / `charge_period_end` | VARCHAR | 事件发生时的自然月边界 |
| `pending_charge_at` | VARCHAR | 下次可重试时间 |
| `retry_count` | INTEGER | 已重试次数（可观测） |
| `charge_error` | VARCHAR | 最后一次失败的**原因码**（可观测） |
| `charged_at` | VARCHAR | 扣分成功时间 |

⚠ SQLite 的 `create_all` **不改已有表** ⇒ 配套**幂等 ALTER 迁移**
（`services/credit_usage_event_migration.py`），且**与建表同批部署**（否则首次写入就报 `no such column`）。

## 四、桌面端：事件带 user_id

- `usage-reporter.js` 新增 `setOwnerSubjectProvider(fn)`（**后绑定**：reporter 在 phase1 构造、identityService 在 phase3 才建）
  ⇒ 仓内已有同款先例（`store` / `accountManager` / `runStateStore` / `taskQueue` / `scheduler` 的 `setOwnerSubjectProvider`）。
- `phase3-services.js` 把**同一个** provider 挂给 reporter（与上面那批同款位置）。
- 事件里带 `user_id`（Logto sub）；**拿不到就留空**（不编造 ⇒ 编一个会污染按用户的成本统计）。
- ⚠ **服务端不会用这个字段扣分**（身份不可信）⇒ 它只用于**按用户维度归集成本**。
