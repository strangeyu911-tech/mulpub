## 〇、一页纸

### 0.1 结论

**「视频创作 → 影视工程 → 自动」这条链路，目前不具备「输入剧本文案 → 自动产出 30 分钟以上短剧成片」的能力。**

不是「差一个时长开关」，而是**七层能力里有六层缺位或形态与预期相反**（分层见 §2.1 L1–L7 与 §0.3 的对照）。把时长常量从 600 改成 1800 只能得到「一条更长的、缺内容骨架的、花几倍 API 费且容易被限流打断的镜片段合集」。

> **2026-10-25 进展**：**M0 门已闭合**（§3.2）⇒ 两个**前提**确认成立：
> ① provider **隐式产出对白音轨**（「对白交给视频模型」成立）；② 镜长**全档可控**（R3 冻结为档 1）。
> ⚠️ 但**前提成立 ≠ 能力具备** ⇒ 上面的结论**不变**：七层里六层仍缺位。
>
> **2026-10-25 后续**：实测暴露的三个**存量缺陷**已全部落地修复 ——
> ③ 进度恒显 `0/N`（§3.2.5.1，#4443 已合并）；
> ① 批内并发与串行 provider 冲突 + ② 幽灵请求雪崩（§3.2.5.3，本版）
> ⇒ **「先修缺陷、再开规模」的前置已解除**，M1 可启动。

### 0.3 六层地基（缺一不可）

> 与 §2.1 的 **L1–L7** 分层对应：L1+L2 ⇒ ① 规模域；L3 ⇒ ② 内容密度；L4 ⇒ ③ 叙事结构；L5 ⇒ ④ 角色与声画；L6 ⇒ ⑤ 提示词质量；L7 ⇒ ⑥ 经济性与治理 + 运行资源。

| 层 | 现状 | 目标 | 备注 |
|---|---|---|---|
| **① 规模域** | 时长 10–600s / 镜数 ≤120 / 剧本 ≤10000 字 | 1800s / ≤360 镜 / ≤36000 字 | 字数比时长更紧（§2.3） |

## 一、目标与边界

### 1.1 目标

把「自动」模式从「一段文案 → 一条 10 分钟以内的无声镜片段合集」升级为
「一部剧本文案 → 一部 30 分钟以上、有对白、有分集结构的短剧成片」，
且该过程**在用户侧是一次确认 + 一次点「开始」**，全程可停可续、失败可见、成本可预估。

### 1.2 硬约束

| # | 约束 | 落实方式 | 对应需求 |
|---|---|---|---|
| C1 | **越简单越好**：用户只给「剧本文案 + 可选人物/场景参考图 + 横竖屏 + 大概时长」 | 5 项输入不变；分集数、镜数、角色数全部由程序推导 | R1 / R6 / R12 |
| C2 | **全部复用影视工程既有底层资产** | kit 模板块结构、剧本套用引擎、角色槽位机制、参考令牌、参考图注入、分批驱动 + 台账 + 磁盘双核续跑、film_render 合成、原文直送合同 | 全部 |
| C3 | **对白与声音由视频生成模型统一完成**（不再单独做 TTS/旁白/BGM 音轨层） | 应用侧不产出音频流；**改为确保「提示词里台词结构化 + 镜长装得下台词 + 角色声音锚一致」** | R3 / R4 / R5 |
| C4 | **生成后可修改调整某个片段** | 保留现有单镜编辑 + 原子覆盖重生成 | R12 |
| C5 | **成本可预估、可控** | 补单价表 → 确认卡显示金额 → 接入 governor → 任务级算力闸 | R8 |
| C6 | **产物可验证** | 端到端集成测试必须真跑出 `final.mp4` 并断言音轨/时长 | R11 |

### 1.3 非目标

- **不做 TTS / 旁白 / BGM / 音效 / 字幕层**（C3 已定：音画由视频模型统一产出）。
  - 例外：若后续要「字幕」，它属画面元素而非声音，且可复用 `story2video-compose-engine.js:589+` 的 drawtext 烧录能力，列为 P2 可选项，不进本方案主干。
- **不做视频剪辑**（时间线、多机位、关键帧编辑）：沿用上游 PRD §14.8 的既定边界，仍只做「改提示词 → 重生成单镜」。
- **不扩 provider 参考输入能力**：仍限既有能力表（`video-reference-inputs.js:30-34`）。
- **不改 kit / schema / 六阶段语义 / checkpoint 语义**。
- **不做多语言/多配音版本**。
- **不改「不经 pipeline 引擎执行出片」这条架构选择**（上游 PRD §14.8 明确列为不做）：
  改为**在自动模式自己的出片出口补上与引擎同等的治理装置**（R8），而不是把执行搬回引擎。

## 二、现状取证：能力分层矩阵

### 2.1 七层能力分层（逐层判有无）

| # | 能力层 | 问的问题 | 现状 | 判定 |
|---|---|---|---|---|
| L1 | **时长/规模** | 能出多长的片子？ | 时长 10–600s；镜数 ≤120；剧本 ≤10000 字 | ❌ **阻断** |
| L2 | **内容密度** | 30 分钟的台词装得下吗？ | 10,000 字 ÷ 1800s = **5.6 字/秒**，低于 `normal` 档（8 字/秒）30% | ❌ **阻断** |
| L3 | **台词-镜长契约** | 台词念得完吗？ | 逐镜 `durationSec` **算出来了但没接到出片**（`auto-runner.js:163` 用的是全局 `shot.seconds`）；**实测：70 字台词推算 10s 却出 5s 片且无逐镜警告；100 字台词 W9 明说「必须拆解台词、不得截断」但照样出 5s 片** | ❌ **缺位（且今天就存在）** |
| L4 | **叙事结构** | 有集、有钩子、有全剧终吗？ | 全目录 grep `episode\|分集\|幕\|全剧终` = **0 命中**；扁平镜列表 | ❌ **缺位** |
| L5 | **角色与声画** | 角色够多吗？声音跨镜一致吗？ | 4 个固定槽位（`ROKO/JAXX/LULU/REIN`，**是参考片的角色**）；提示词无结构化台词；无角色-声音锚 | ❌ **缺位** |
| L6 | **提示词质量** | 提示词是「你的剧本」还是「参考片模板 + 你的文案」？ | 实测**模板几乎不参与**（保留率中位 0.10%，82% 的模板产出 ≤200 字符）；但也因此**影视工程方法论在自动模式下基本没接上**；LLM 已下线 | ⚠️ **缺位（形态与预期相反）** |

### 2.3 关键取证：规模域的硬算术

**语速常量**（`shot-duration.js:37`）：`ZH_CHARS_PER_SECOND = { normal: 8, argument: 10, tender: 5 }`（字/秒）

| 目标时长 | 纯对白所需字数（normal 档） | 所需镜数（5s/8s/10s/12s 档） | 撞现有上限？ |
|---|---|---|---|
| 600s（现状上限） | 4,800 字 | 120 / 75 / 60 / 50 | 镜数刚好卡 120 |
| **1800s（目标）** | **14,400 字** | 360 / 225 / 180 / 150 | **镜数与字数双双超** |

**镜数下限**（30 分钟最少需要多少镜）：
- 5s 档 → 360 镜
- 8s 档 → 225 镜
- 10s 档 → 180 镜
- 12s 档 → 150 镜
⇒ **无论选哪档，都超 `MAX_AUTO_SHOTS = 120`**。必须提到 ≥180（10s 档）才能覆盖 30 分钟。

**字数上限才是更紧的那道锁**（这是最容易漏算的一条）：
- 30 分钟纯对白 = **14,400 字**（与镜数无关，只与总时长有关）
- 短剧对白占比通常 40–60%，其余是动作/场景描述 ⇒ **剧本总量 ≈ 24,000–36,000 字**
- 现状 `MAX_AUTO_SCRIPT_LENGTH = 10000` ⇒ **差 2.4–3.6 倍**
- 反向看：10,000 字 ÷ 1800 秒 = **5.6 字/秒**，比 `normal` 档慢 30%、比 `tender` 档只快 12%
  ⇒ **若不抬字数上限，30 分钟成片的台词密度将低到近乎旁白/静场，而不是短剧**

> **结论**：R1 必须同时放开**时长、镜数、字数**三项。
> **字数目标取值 = 36,000**（覆盖上界，不是取中位数）——理由：若取 30,000，则对白占比落到 ~40% 以下的剧本会被拒，
> 而「对白占比」是经验值不是契约，**上限应按最坏情况取**，宁可放宽也不要让用户撞到一个说不清的数。
> 剧本输入框的交互形态（`el-input type=textarea :maxlength=10000`）也要跟着改，否则前端先卡死。

### 2.4 关键取证：模板在自动模式下几乎不参与（实测）

`apps/desktop/electron/film-kit/shot-library.json` 实测：**153 镜**（对应 153 个 `sceneId`；`film-manifest.json` 声明 162 场，其中 **9 场无对应镜**，是「精选模式每场取 1 条代表镜」的结果），
4 个角色（`ROKO/JAXX/LULU/REIN`），`filmMeta.durationSec = 5706`（95 分钟）。

**模板块结构分布**（153 镜中）：

| `[CHARACTER: X]` 行 | **0** | 0 | **随包 kit 里 `[CHARACTER:` 出现 0 次 ⇒ `characterLines` 恒空** ⇒ 模板角色槽位名**根本不在提示词里** |

⇒ **进入提示词的模板内容 = 45 块 / 3,609 块 = 1.25%。**

**实测：模板内容到底有多少进了提示词。**
逐个模板单独跑一次 `planAutoShots`（脚本固定为一句台词），量它单独贡献的提示词长度：

| 指标 | 实测值 |
|---|---|
| 模板原文 prompt 长度 | 均值 **16,055** 字符（最大 39,468） |
| 单镜提示词长度（模板 + 用户一句台词） | 中位 **16** 字符、最大 12,326 |
| **保留率** | 中位 **0.10%** |
| 产出 ≤200 字符的模板 | **125 / 153（82%）** |
| 产出 ≤500 字符的模板 | 133 / 153 |

**三条推论**：

1. **参考片模板在自动模式下几乎不参与。** 3,609 个正文块只有 45 块（1.25%）进入提示词；
   82% 的模板对提示词的贡献不超过 200 字符，中位贡献 16 字符（就是用户自己那句台词）。
   ⇒ **好消息**：原片世界观、角色形象、`EXACT` 硬约束、原片角色槽位名**都不会**被带进用户剧
   （随包 kit 里 `[CHARACTER:` 为 0 ⇒ 连槽位名都不在提示词里）—— 「模板中立化」这个担忧在当前实现下**基本不存在**。
   ⇒ **真缺口**：**「影视工程方法论」在自动模式下基本没接上**。用户得到的是「自己的文案被原样送进视频模型」，不是「按影视工程方法论组织的提示词」。
2. **「三分提示词」机制在随包 kit 上基本空转。** `buildMotionPrompt`（`script-adapt.js:147-150`）只保留 `head + characterLines + motionParts`，而 153 个模板里 150 个没有 `ACTION TIMING`、0 个有 `CHARACTER ACTING` ⇒ 对绝大多数镜，**videoPrompt ≈ imagePrompt**。
   ⇒ 这也意味着：**用户的中文台词在 videoPrompt 里是安全的**（`head` 含剧情行，`script-adapt.js:78-79`），不会因为静态块剔除而丢失。
3. **16% 的模板带 `AUDIO` 块，而它被归为静态类、从 videoPrompt 里剔除。** 在 C3 前提（视频模型负责对白与声音）下，**AUDIO 块恰恰是最该给视频模型的语义**，却被当成「静态空间地图」剔掉了。
   ⇒ 这是 C3 前提与既有三分规则的一处**直接冲突**，必须在 R4 处理（见 §四 R4）。

### 2.6 关键取证：合成层对带音轨片段的处理

好消息：**合成层已经能正确处理带音轨的片段**（探针 → 一致性判据 → 统一转码 → concat），不需要改。
⚠️ 口径提示：合成层做的是**音轨的规格统一**，**不做音轨语义处理**（混音 / BGM / 响度归一 / 字幕 / 转场一律没有）。

⇒ R10 需要评估「先统一规格再合成」与「逐镜归一」两种路径的成本差。

## 三、必须先做的三个前置取证（M0 门）

### F-1 目标 Provider 是否真的产出对白音轨？

**问题**：C3 假设「对白和声音交给视频生成模型统一完成」。但 9 个视频适配器**无任何 audio 参数**。
两种可能：
- (a) provider **隐式**产出音轨（模型自带原生音频能力，adapter 只需传 prompt）⇒ 前提成立；
- (b) provider 需要**显式开关**（如 `generate_audio: true` / `audio: true`）⇒ 前提不成立，**当前链路出的是哑片**。

**取证方法**（M0 阶段做，不进主干）：

```bash
# 1) 造一条带对白的提示词，走 film-engineering 的实际提交路径
#    （用 apps/desktop/electron/services/film-engineering/video-gen.js:158 generateShotVideo）
# 2) 产物落盘后探测音轨
ffprobe -v error -print_format json -show_streams shot_000.mp4 | \
  python3 -c "import json,sys; s=json.load(sys.stdin)['streams']; \
  a=[x for x in s if x['codec_type']=='audio']; \
  print('音轨流数 =', len(a), a[0] if a else '（无）')"
```

**判据**：
- 有 audio 流 ⇒ 前提 (a) 成立 ⇒ 走 §四 全套需求；
- 无 audio 流 ⇒ 前提不成立 ⇒ **本方案 R3/R4/R5 全部作废**，改为「先补适配器音轨开关 + 建 provider 音轨能力表」，长篇化降级为 P1。

**附带产出**：一张 `VIDEO_AUDIO_CAPABILITY_BY_PROVIDER` 音轨能力表（**已落地** = §3.2.5.6；
形态取自 `video-reference-inputs.js` 的 `Object.freeze` 映射 + 保守探测，但**条目是「能力」不是「参数名」**），
让规划期能区分「**这个 provider 的音轨从哪来**」，而不是等 15 小时跑完才发现。
⚠ **但「未实测」不能当成「不产对白」来告警**（未实测 ≠ 不支持）⇒ 详见 §3.2.5.6 的三态设计。

### F-2 目标 Provider 是否接受应用下发的镜长？

**问题**：`buildShotSubmitPayload`（`video-gen.js:73-100`）下发 `numFrames / width / height / frameRate`，
但只有 2/9 的适配器消费。若 provider 忽略帧数，**镜长由 provider 默认决定**（通常 5s 或 10s 固定）。

**取证方法**：同一提示词，分别下发 **121 / 201 / 241 / 289** 帧（289 = 12 秒档，R1 新增，**必须一并测**），
探测每次成片的实际时长，填成**逐档对照表**：

| 下发帧数 | 5s 档 | 8s 档 | 10s 档 | 12s 档 |
|---|---|---|---|---|
| 实际成片时长 | ? | ? | ? | ? |

**判据（必须是三态，二值不够）**：
- **全档可控**（每档时长都随下发变化且≈对应档）⇒ R3 走「档 1」（严格台词-镜长契约）；
- **部分可控**（部分档生效、部分被 provider 钳到固定时长）⇒ **R3 需要第三档形态**：
  逐镜在「实际可控的档」里选帧，**不可控的档强制走拆镜**；
- **全档不可控**（时长恒定）⇒ R3 走「档 2」（把「镜长不可控」转成「镜数变多 + 台词主动拆镜」）。

> ⚠️ **为什么不能用二值判据**：真实 provider 常见的就是「支持 121/201 但把 241 钳到固定时长」的**部分可控**形态，
> 二值判据会把它误判成「全可控」或「全不可控」，从而在错误前提上冻结 R3 的形态。
> ⚠️ **`ltx` 需单独实测**：其帧数语义与 `agnes` 不同（`num_frames` 缺省 24 帧 ≈ 1 秒，不是「总帧数」）。

**两种形态的 R3 实现差异见 §四 R3。**

### M0.6 落盘体积实测（本次已完成 —— 结论：R13 的体积担忧被证伪）

**口径**（方案 A24）：`prompt.length` 的 P50 / P95 × 镜数 × 3 份副本（`prompt` / `imagePrompt` / `videoPrompt` 三份相同的长文本）。

**样本**：真实随包 kit（153 镜）+ 40 段真实剧本 ⇒ 产出 40 镜。

| 指标 | 实测值 |
|---|---|
| `prompt.length` 最小 | **44** |
| `prompt.length` P50 | **46** |
| `prompt.length` P95 | **1251** |
| `prompt.length` 最大 | **3802** |

**推算（三副本）**：

| 镜数 | P50 三副本 | P95 三副本 |
|---|---|---|
| 120（当前上限） | 0.02 MB | **0.43 MB** |
| 360（M1 放开后的目标） | 0.05 MB | **1.29 MB** |

⚠️ **口径说明**：上表按**字符数**折算字节（`prompt.length × 镜数 × 3`）。
中文在 UTF-8 下是 3 字节/字 ⇒ 真实字节体积约为 3×（360 镜 P95 约 3.9 MiB）⇒
**结论不变**（相对 8MB/镜 口径仍是 0.13% 量级 ⇒ JSON 体积可忽略）。

**结论**：
1. **JSON 文本体积可以忽略** —— 360 镜的 P95 三副本仅 **1.29 MB**，而仓库现有的磁盘预估口径是
   **8 MB/镜**（`auto-plan.js` 的 `DISK_ESTIMATE_BYTES_PER_SHOT`）⇒ 360 镜 = **2880 MB**。
   ⇒ **提示词文本只占 0.045%** ⇒ 磁盘占用的真正大头是**视频文件**，不是 JSON。
2. ⚠️ **分布是长尾的**（P50=46 而 P95=1251、最大 3802）⇒ 这与 §2.4 的实测一致：
   模板几乎不参与自动模式的提示词拼装（保留率中位 0.10%）⇒ 多数镜的提示词短到只有用户那句台词。
   ⇒ **凡是用「平均长度」估体积的判据都会低估** ⇒ 必须用 P95。
3. ⇒ **R13 的「落盘体积」子项可以降级**：JSON 侧不构成风险；R13 的真正风险在
   **长任务期间的并发度与内存**（该子项随 M5 保留）。

### 3.2.4　本次实测暴露的三个真实缺陷（**存量缺陷，非长篇化引入**）

#### ① 批内并发 2 与 provider 串行受理冲突 ⇒ 提交卡满 120 秒 ⇒ 单镜判 failed

`PRODUCTION_BATCH_CONCURRENCY = 2`（`production-runner.js:14`，**硬编码、无配置项**），
而该 provider 的视频提交**近似互斥受理**（成功提交之间的时间重叠率 0/6）⇒ 第二个请求在队列里等满 120 秒
⇒ 抛 `provider request timed out after 120000ms` ⇒ 该镜判 failed。

#### ② 客户端超时 ≠ 服务端停止 ⇒ 失败请求变成滞留队列的「幽灵请求」⇒ 重试自我放大成雪崩

**这是本次最硬的机制发现**（比 ① 更强）：

- 客户端 120s 超时只让**客户端**放弃等待，**服务端很可能仍在生成** ⇒ 该请求占着串行受理通道；
- 可复算读数：最近 215 次 `generateVideo` 中成功 112、失败 103，**失败中 102 次卡满 120000ms**；
  成功请求耗时**中位数 725ms**（提交即返回、生成异步轮询）、**P90 95.7s**、最大 218.5s、平均 26.6s；
- 按 `102 × 26.6s` 估算 ⇒ **队列排空需约 45 分钟**；
- 实测时间线：最后一次成功后，其后**六个 10 分钟桶成功率全部为 0%** —— 期间每一轮重试都在往队列里**再加**请求；
- ⚠️ **适配器内部 6 次尝试（退避 20/30/45/60/60 秒） × 上层重试 ⇒ 单镜最多向 provider 投出 78 个请求**
  ⇒ 在串行 provider 上等于**请求洪水**；
- ⇒ **决定性对照**：静默 11 小时（队列已排空）后，**第一个单发请求 20.4 秒即成功**
  ⇒ 证实主因是**队列饱和**，「并发 2」是**放大器**。

⇒ **产品影响**：**光把批内并发降到 1 不够**；真正的闸门是
「**客户端超时后不得立即重投同一个请求**」，且退避时长要按 **provider 队列长度动态计算**
（固定 90–120 秒实测**不够**）。

#### ③ 状态回写发生在「批次收口」时，不是逐镜 ⇒ 面板在执行期间显示 `0/N`

批次执行中，`auto-status` 的 `doneCount` 恒为 0、每镜 `status` 恒为 `pending`，
**磁盘产物却已在增加** ⇒ 判进度**必须以磁盘为准**（影响 §四 R11）。

#### 3.2.5.1　缺陷 ③（进度恒显 0/N）——✅ 本版已落地

**数据校验**（新增读数 `doneCountOnDisk`）：

**功能逻辑（两个口径必须分开，不可合并）**：

| 口径 | 取值 | 用途 |
|---|---|---|
| `displayDone` | `max(台账 done, 磁盘已落盘)` | **仅用于显示**（面板进度 / 百分比） |

> 若拿磁盘口径做收口判定，会在产物还在落盘时**提前收口**。
> ⇒ 落地形态：两个口径由**同一个纯函数**一次产出（`resolveProgressCounters`，`auto-progress-counters.js`），
> 且**分别命名** ⇒「用错口径」变成一次显眼的取值，而不是隐式约定。

⚠ **补记（2026-10-26，§3.2.5.5 落地后回看本节）**：「已落盘 N / M」这句在**执行期**其实是**不准确**的
—— N 只能来自磁盘口径（已落盘的片数），而「磁盘有片 ≠ 该镜成功」（可能是上一轮残留，也可能该镜最终被判失败）

（**只承诺落盘，不承诺成功**），收口后才说「已完成 N / M」（那时 N 来自台账，每镜都有结论）。

#### 3.2.5.2　缺陷 ① + ②（并发 2 × 串行 provider ⇒ 幽灵请求雪崩）——✅ 已落地（实现见 §3.2.5.3）

**为什么必须成套**：
缺陷 ② 的「超时后不立即重投」**单独**落地 ⇒ 原本靠重投掩盖的「队列已饱和」会**立刻**变成
「快速缺镜」⇒ **用一种坏换另一种坏**。
⇒ 必须同时有：①（少投一个请求）②（饱和时熔断并等待）③（进度可观测）三条。

**数据校验（超时必须分两类，现在被混成一个码）**：

| 类 | 识别 | 语义 | 是否可立即重投 |
|---|---|---|---|
| **客户端等待超时** | 我们的 `AbortController` 计时器放弃（`error.name === 'AbortError'`） | **请求已被受理，服务端很可能仍在生成** | ❌ **不可重投**（重投只会加长队列） |
| **连接层超时/网络错误** | TCP 层 `ETIMEDOUT` / `ECONNREFUSED` / `ENOTFOUND` | 请求**根本没到** | ✅ 可重投 |

> ⚠ 现状：`agnes-multimodal.js::_request` 把两者都抛成 `ERROR_CODES.TIMEOUT`
> ⇒ 而 `generateVideo` 的可重试判据里 `error.code === ERROR_CODES.TIMEOUT` **在列**
> ⇒ **每次客户端超时都会退避 20/30/45/60/60 秒后再投一次** ⇒ 每次重投都在**服务端仍在生成**的通道上再加一个请求。

**饱和判定（数据源：`model_provider_logs` 的该 provider 近期视频提交记录）**：

| 指标 | 定义 | 阈值（建议） |
|---|---|---|
| 连续客户端超时 | 最近连续 N 次视频提交以「客户端等待超时」结束 | **N = 3** |
| 近窗口超时率 | 近 20 次视频提交里客户端超时占比 | **≥ 50%** |
| 有效并发 | 观测到「成功提交之间的时间重叠率」≈ 0 ⇒ 串行受理 | ⇒ 视频 provider 的**有效并发 = 1** |

**队列排空估计（退避时长不能是固定常数）**：

```
滞留请求数 = 近窗口客户端超时次数（未完成的请求）
平均生成耗时 = 该 provider 近期**成功**提交的平均耗时（实测中位数 725ms、P90 95.7s、最大 218.5s）
预计排空时间 ≈ 滞留请求数 × 平均生成耗时
```

> ⚠ 实测：102 条滞留 × 26.6s ≈ **45 分钟** ⇒ **固定 90–120 秒退火恢复不了**（实测退火 120s 后仍零成功）。
> ⇒ 退避时长**必须由队列长度推导**，不得写死。

**功能逻辑（状态机）**：

```
未饱和 ──(连续超时 ≥ N 或超时率 ≥ 50%)──► 饱和
   ▲                                          │
   └────(窗口内无超时且成功率恢复)──────────────┘
饱和态：① 视频批内并发降为 1（有效并发 = 1）
        ② 停止向该 provider 派发新镜（熔断）
        ③ 按「预计排空时间」等待（不是固定退避）
        ④ 等待期间不重投同一请求
```

**交互逻辑**：熔断/等待期间，面板**不得**显示「失败」或「0/N」⇒ 应显示「等待 provider 恢复」。

**显示项**：
- 面板运行态新增一项「provider 状态」：正常 / 饱和（等待）/ 已熔断；
- 恢复后该提示自动消失（不留历史痕迹）。

**提示文字**（zh / en 成对）：

| 场景 | 中文 | English |
|---|---|---|
| 饱和等待 | 「服务商繁忙（{pending} 个请求排队中），已暂停提交，预计 {minutes} 分钟后恢复」 | 「Provider is busy ({pending} requests queued); submissions paused, resuming in about {minutes} min」 |
| 恢复 | 「服务商已恢复，继续提交」 | 「Provider recovered; resuming submissions」 |
| 单镜因饱和未提交 | 「该镜未提交（服务商繁忙），恢复后可单独重生成」 | 「This shot was not submitted (provider busy); you can regenerate it after recovery」 |

#### 3.2.5.3　缺陷 ① + ② 的**实现落点**（2026-10-25，✅ 本版已落地）

> ⚠️ 本节是对 §3.2.5.2 规格的**实施订正**：落地时用实测数据把三处口径收紧了。
> 订正逐条写在「订正理由」列 —— 是**前提更精确**，不是「原论证错了」。

##### 三处口径订正（与 §3.2.5.2 的差异）

| # | §3.2.5.2 的写法 | 落地口径 | 订正理由 |
|---|---|---|---|
| 1 | 「**饱和态**：① 视频批内并发降为 1」 | **恒定**降为 1（不只在饱和态） | 串行 provider 上并发 2 时，第二个请求**必然**在队列里排队 ⇒ **必然**撞客户端等待上限 ⇒ 「饱和」是并发 2 的**必然结果**而非偶发事件 ⇒「等饱和了再降并发」来不及，第一对并发请求就会制造幽灵请求 |
| 2 | 「平均生成耗时 = 近期**成功提交**的平均耗时」 | 排空估计用**实测均值 26.6s** | 同一份实测分布给出四个数：`<20s` 66 条 / `20-50s` 21 / `50-95s` 10 / `95-120s` 9 / `>=120s` 6 ⇒ **中位数 725ms**（提交即返回）、**均值 26.6s**、**P90 95.7s**、**最大 218.5s**。中位数是「提交往返」的快路径（provider 忙时提交要排队）⇒ 用它会**严重低估**；P90 会**高估 3.6 倍** ⇒ 白等。取均值才与「102 × 26.6s ≈ 45 分钟」同源 |
| 3 | 饱和判定数据源 = `model_provider_logs` | **进程内观测窗口**（适配器侧记录 + 批执行器侧读取） | 熔断必须**实时**；DB 查询有秒级延迟，且主进程无该表的访问路径 ⇒ 用 DB 会让「停止派发」慢到失去意义。⚠ 诚实边界：`model_provider_logs` 仍是**事后复算**的真源；本模块是**运行期**的近似 |

##### ④ 超时的两类判据（**实测形态**，不是推测）

| 类 | 识别依据（实测） | 语义 | 是否可立即重投 |
|---|---|---|---|
| **客户端等待超时** | `error.name === 'AbortError'`（`DOMException`，`code=20`，**无 cause**） | 我们的计时器放弃 ⇒ 请求**已被受理**，服务端很可能仍在生成 | ❌ **不可重投** |
| **连接层失败** | `error.cause.code ∈ {ETIMEDOUT, ECONNREFUSED, ENOTFOUND, UND_ERR_SOCKET, …}` | 请求**根本没到**服务端 | ✅ 可重投 |

> ⭐ **实测纠正了一条一直写错的判据**：现有代码查的是 `e.message` 里的 `'ETIMEDOUT'`，
> 而 **undici 的 `e.message` 恒为 `"fetch failed"`**，真实错误码在 **`e.cause.code`**。
> ⇒ 那条判据**对 undici 永远匹配不到** ⇒ 连接层错误其实**从未**被识别成 `TIMEOUT`，
> 而是一直掉进 `NETWORK_ERROR` 分支（行为上仍可重试所以没炸，但**错误码是错的**）。
> ⇒ 「两类超时被混成一个码」的真实机制在此：**不是合并，是连接层那类压根没被分类**。

##### ⑤ 视频提交的客户端超时：120s → **240s**

- 串行 provider 上「提交」要排队 ⇒ 实测成功请求耗时**最大 218.5s**
  ⇒ 用 120s 会把「慢但正常」的请求变成「客户端放弃、服务端仍在生成」的**幽灵请求**。
- 取 **240s**：覆盖实测最大服务时间；且**远小于** `callAdapter` 给视频类的外层预算（10 分钟）
  ⇒ **内层先超时** ⇒ 错误能带上 `timeoutKind` 分类（否则外层兜底会把分类抹掉）。
- 可由 `options.videoTimeout` 覆盖。

##### ⑥ 饱和检测与熔断（功能逻辑）

```
未饱和 ──(连续客户端超时 ≥ 3  或  近窗口超时率 ≥ 50%)──► 饱和
   ▲                                                       │
   └────(窗口内无超时且成功率恢复)───────────────────────────┘

饱和态：① 停止向该 provider 派发新镜（熔断）
        ② 按「预计排空时间」等待（**不是固定退避**）
           预计排空时间 = 滞留请求数 × 单请求平均服务时间
           运行期等待封顶 5 分钟；真实预计恢复时间照常显示
        ③ 等待后**重新判定**：已恢复 ⇒ 继续派发；仍饱和 ⇒ 本镜判「未提交（服务商繁忙）」
        ④ 等待期间**不重投**同一请求
```

- **窗口口径（速率视角）**：最近 **20** 次提交 + 最近 **30 分钟**（有界 ⇒ 半小时前的超时不会继续熔断今天的批次）。
- **超时率判据需要样本量**：窗口不足 3 条时**只认连续判据**（否则「1 次超时 / 1 次成功」= 50% 会误判）。
- **有效并发恒为 1**（见订正 ①）⇒ 我方对队列的贡献最多 1 个请求。
  ⚠ **两处都要降**：自动模式（`auto-runner.js`）**与**全量出片（`video-gen.js` 的 `film_generate_videos`
  原先 `requestedConcurrency` 默认 **2**）⇒ 已一并降为 1（需要并发的 provider 可显式配 `stage.options.videoConcurrency`）。

#### ⑥.1 ⭐ 「滞留」与「速率」必须分成两个量（2026-10-25 独立复核抓到的阻断缺陷）

**问题**：原设计把「滞留请求数」取自「近 20 条窗口」⇒ 两个后果：

1. **排空估计被封顶** ⇒ 「102 条滞留 × 26.6s ≈ 45 分钟」这个实测结论**永远算不出来**（最多 8.9 分钟）；
2. ⭐ **熔断等待期间不派发 ⇒ 观测窗口不新增记录 ⇒ 窗口内容完全不变**
   ⇒ 「等完再重新判定」**永远**判成「仍饱和」⇒ **等待纯空转**、剩余镜头全灭、恢复提示永不出现。

**机制（落地口径）**：

| 量 | 口径 | 用途 |
|---|---|---|
| **速率** | 近 20 条 + 近 30 分钟的窗口（**过期的客户端超时不算失败**） | 超时率判据 |
| **累积** | 本次运行**全部**且**未过期**的客户端超时（**不被窗口条数封顶**） | 滞留数 / 排空估计 |
| **过期阈值** | 「2 × 观测到的单请求平均服务时间」，夹在 **53.2s**（2×实测均值）~ **218.5s**（实测最大）之间 | 判定「服务端大概率已做完」 |

⇒ **过期**的含义：客户端超时 = 客户端放弃了、**服务端可能还在做** ⇒ 这条请求**会**被服务端做完
⇒ 过一段时间它就不再是「滞留」⇒ **这正是熔断等待期间唯一的恢复信号**（因为熔断时不派发 ⇒ 没有新记录）。
⇒ 熔断等待时长因此必须 **≥ 过期阈值**（否则等完必然「仍饱和」）⇒ 运行期等待 = `min(5 分钟, max(预计排空时间, 过期阈值))`。

#### ⑥.2 跨任务隔离（2026-10-25 独立复核抓到的阻断缺陷）

观测窗口是**模块级**（进程内共享）⇒ **上一轮任务**留下的「客户端超时」会让**新任务的第一镜就直接判饱和**
⇒ 整批一镜不出、用户完全看不懂发生了什么。
⇒ 饱和度是「**本次运行**的观测」⇒ **`auto-start` 时重置该 provider 的观测窗口**（任务边界即其生命周期边界）。
⚠ 真实积压不会因此消失：新任务第一次提交失败后会立刻重新累积 ⇒ 不漏判也不误伤。

##### ⑫ 治理层（governor）：**订正**——它其实看不到那个错误，但分类仍要加

> ⚠ **本节是对上一版结论的订正**（2026-10-25 独立复核实测推翻）：
> 上一版写「只改适配器 ⇒ 全量出片路径仍会把视频提交再投出去」—— **这个结论是错的**。

**实测链路**（`model-provider-manager.js:328-338` → `video-gen.js:200-202`）：

```
适配器抛 ProviderError(TIMEOUT, timeoutKind='client-wait')
  → callAdapter **吃掉**它，返回 { code: -1, error }（不抛）
  → video-gen.js 转成 { success:false, error: 文本 }（**从不抛**）
  ⇒ governor 的 task() **看不到**这个错误 ⇒ **不会**对它重投
```

⇒ ⭐ **真正闭合雪崩的是适配器层**（`isRetryableTimeout(error)` ⇒ 客户端等待超时**不重投**）：
变异去掉它 ⇒ 实跑「客户端等待超时的提交数」从 **1 次变 6 次** ⇒ 锁有牙齿。

⇒ 那为什么还要加 `client_wait` 分类？——**防御性**：
`classifyProviderFailure` 是**通用**分类函数，将来若有路径**真的把 ProviderError 抛出来**
（例如把 `callAdapter` 改成抛、或阶段级重试直接吃异常），
`TIMEOUT` 会被归成 `transient` ⇒ governor 对 transient 会做**有界重投** ⇒ 队列雪崩复发。
⇒ 故新增独立类别 `client_wait`（**仅当带 `timeoutKind='client-wait'` 时命中**；
**普通 `TIMEOUT` 仍归 `transient`** —— 「分不清」时不能砍掉重试能力）。

⚠ **副作用（必须申报）**：`story2video-stages.js:1198` 的 story2video 瞬时重试
按 `classifyProviderFailure` 的类别判断 ⇒ `client_wait` **不再落进它的重试分支**
⇒ story2video 路径上「客户端等待超时」也不再重试。
⇒ 这是**与本缺陷同源**的语义（客户端超时本就不该重投），但属**跨流水线行为变化** ⇒ 已登记。

##### ⑬ 诚实边界（本次**没做**的）


- ⚠ **`model_provider_logs` 侧的历史复算工具没做**：本版只做运行期观测窗口；
  「按 DB 复算某段时间的幽灵请求堆积」仍是 M1 的事。
- ⚠ **`callAdapter` 外层兜底超时（10 分钟）不带分类**：内层 240s 先超时 ⇒ 正常路径下分类完整；
  但若适配器整体卡死在外层兜底里，错误仍是**无分类**的 `TIMEOUT`
  ⇒ 会被 governor 当 `transient` **重试**（这条出口仍未闭合；见 ⑫）。
- ⚠ **单镜重生成路径未接熔断**：`regenerateOneShot` 是单请求、无批上下文 ⇒ 不参与熔断判定
  （但它同样受益于「客户端超时不再重投」）。
- ⚠ **排队估计仍是近似**：滞留请求数是「**累计且未过期**的客户端超时次数」，
  不是服务端真实队列长度 ⇒ 预计恢复时间必然有偏差 ⇒ 面板文案用「预计」而非「将在」。
  ⭐ 已按复核结论把滞留数从「近 20 条窗口」改成「累计」（否则「102 条 ≈ 45 分钟」不可达）。

#### 3.2.5.5　A33　进度提示区分「执行中 / 已收口」（2026-10-26，✅ 本版已落地）

##### 现状（实测，不是读文档推的）

| 环节 | 现状 | 问题 |
|---|---|---|
| 后端 `auto-status` | `running: runningAutoTasks.has(project.taskId)` | ⭐ 这就是「批次还在跑」的**权威信号**（`runningAutoTasks` 在 `auto-start` 派发时同步加入，driver 结束时删除） |
| 渲染端 `useFilmAutoRun.js` | `progress.doneCount` = `displayDone`（磁盘口径 max 台账）⇒ `stageList` 用 `stageShotProgress` 文案 | ⚠ 文案恒为「已完成 {done} / {total} 镜」⇒ **执行期也在说「已完成」** |
| 面板 `FilmAutoPanel.vue` | `:summary` 硬编码 `runSummary` | 同上 |

⚠ **为什么「执行中说『已完成』」是在说谎**：逐镜状态**只在批次收口时**才回写台账
⇒ 执行期台账里每镜仍是 `pending` ⇒ 那个 N **只能来自磁盘口径**（已落盘的片数）
⇒ 而「**磁盘有片 ≠ 该镜成功**」（可能是上一轮残留，也可能该镜最终被判失败）
⇒ ⇒ 说「已完成」会让用户以为这 N 镜**已经成了** ⇒ 收口后若其中有镜失败，用户被误导过。

##### ⭐ 判据：只用 `running`（**单一真源**），且**不能用 `phase` 代替**

| 候选判据 | 为什么不采信 |
|---|---|
| `phase === 'running'` | ❌ `phase` 是**渲染端**的阶段值：任务中断（失败/停止）时后端 `running=false`，但 `phase` 会**停在 `'running'`** ⇒ 会把「**已经停了**」说成「还在落盘」⇒ **那是在骗用户** |
| 事件负载（`production:*`） | ❌ 事件**不带 `running`** ⇒ 只有轮询能给出权威值 ⇒ 事件参与判定 ⇒ **两处口径打架** |
| `displayDone > closeDone`（双口径比较） | ❌ 只能区分「磁盘领先台账」⇒ 分不出「**第一镜还没落盘**」与「**已经停了**」两种都等于 0 的情形 |
| ⭐ **`data.running === true`（后端 `auto-status`）** | ✅ 精确等于「这个任务当前在主进程里跑着」⇒ **批次还在跑**；且**只有轮询能给权威值** ⇒ **单点** |

⇒ 落点：`useFilmAutoRun.js` 的 `refreshStatus` 里 `batchRunning.value = data.running === true`
（**事件不改它** ⇒ 避免两处口径打架；`production:complete` 事件会触发 `refreshStatus()` ⇒ 收口瞬间即拿到 `false`）。

#### 3.2.5.6　M0.4　音轨能力表（2026-10-27，✅ 本版已落地）

**产出物**：`apps/desktop/electron/services/film-engineering/video-audio-inputs.js`
（`VIDEO_AUDIO_CAPABILITY_BY_PROVIDER` + 三态探测函数）+ `video-audio-inputs.test.js`（16 例）。

##### ⛔ 为什么是**三态**（`implicit` / `explicit` / `unknown`），不是二态

「音轨支持 / 不支持」这个二态**会骗人**：
- `agnes-multimodal`：**模型自己产音轨**（实测 51/51 产物带 `aac`）⇒ `implicit`（**不需要**显式开关）；
- `heygen`：**有显式音轨参数**（数字人 `voice` + `script`）⇒ `explicit`；
- 其余 13 个：**读源码未见音轨参数，但产物未验证** ⇒ `unknown`。

⇒ ⭐ **`unknown` ≠「不支持」** ⇒ 探测函数**不能只返回布尔**（否则两者同形）
⇒ ⇒ `resolveVideoAudioCapability()` 返回**结构化对象** `{ mode, audioParam, audioSource, verified, evidence }`；
⇒ ⇒ `isVideoModelProducedAudio()` 对 `unknown` 返回 **`null`（未知）**、不是 `false`（不满足）。

##### ⭐ 域 = **15 个**视频 provider（权威判据，**不靠人工名单**）

**判据 = `adapter.supports('generateVideo') === true`**
（`adapters/_base/base.js`：`KNOWN_METHODS` 含该方法 **且** 实例的 `generateVideo` **不等于** `BaseAdapter.prototype.generateVideo`
⇒ 只「提及」不算，只「继承基类默认实现」也不算）。

实测集合（**15 个**）：`hunyuan` / `cogvideo` / `grok-video` / `heygen` / `kling` / `runway` / `veo` / `wan` /
`minimax` / `minimax-multimodal` / `agnes-multimodal` / `ltx` / `seedance` / `higgsfield` / `agnes-video`。

⚠ **两个易错口径**：
- ⛔ 仓内注册表 `model-provider-manager.js` 那段注释写「视频生成 (14)」⇒ **数字也不准**（该区块实为 16 条目，
  其中 `hifly` 是数字人类、**不支持** `generateVideo`）⇒ **以 `supports()` 实测为准**；
- ⛔ `comfyui` **不是**视频 provider（注册在图像区块）⇒ 旧口径把它算成视频适配器是错的。

⇒ ★ **表覆盖全部 15 个**（不是「只列测过的那一个」）
⇒ ⇒ 否则「**漏列**」与「**未实测**」在读数上同形（前者是缺陷、后者是事实）⇒ 机械锁双向比对（漏列/多列都红）。

##### ⛔ 域的边界：本表**不是**「仓里有没有 TTS」

本表的域 = **「视频适配器的音轨产出方式」** ⇒ 仓内的 `doubao-tts` / `elevenlabs` / `mimo-tts` / `minimax-tts` /
`google-tts` / `openai-tts` / `suno` / `musicgen` / `pixabay-music` / `freesound` / `local-whisper` …
**全部不属于本表**（那是独立的语音/音乐能力，不是「视频出片时音轨从哪来」）。
⇒ ⚠ **`minimax-multimodal` 是这个边界最容易踩的** ⇒ 它**有** `synthesize` / `listVoices` / `cloneVoice`（TTS 能力），
但它的 `generateVideo` **转发给 `minimax.js`**（载荷 = `model/prompt/duration/resolution/first_frame_image/prompt_optimizer`，
**无音轨字段**）⇒ **仍判 `unknown`** ⇒ 「有 TTS 能力」**不等于**「视频出片有音轨」。

##### ★ `audioSource`：音轨的**来源类别**（`mode` 之外的第二个维度）

| `audioSource` | 含义 | 满足「音轨交给视频模型」前提？ |
|---|---|---|
| `model` | 音轨来自**视频模型本身** | ✅ 满足 |
| `tts` | 音轨由**独立 TTS / 数字人**驱动 | ⛔ **不满足** |
| `null` | 未实测 | ⚠ 未知（不是「不满足」） |

⇒ `heygen` = `explicit` + `audioSource: 'tts'` ⇒ ⚠ **它不满足本仓前提**
（HeyGen 的 `generateVideo` 是**数字人视频**：`params.character` / `params.voice` / `params.script` **三者必填**，
音轨 = `voice{type:'text', input_text:script, voice_id:voice}`）⇒ 声音来自 TTS，不是视频模型。
⇒ ⇒ **规划期若选它，音轨来源要另行说明**（这是**前提不适配**，不是缺陷）。

##### ⛔ `agnes-multimodal` 的 `params.audios` **不得**填进 `audioParam`

它（≤3 个）是 **reference 模式的参考音频 URL 列表**（**输入素材**），
**不是**「生成对白」的开关 ⇒ 填进去等于宣称「传 3 段参考音频就能开对白」⇒ 那是假的。
⇒ ⇒ `audioParam` 必须是 `null`（有机械锁盯着）。

### R2 内容密度：字数 / 时长的换算口径显性化

**现状**：三者（字数、时长、镜数）各自独立校验，**没有任何一处告诉用户「你要的 30 分钟需要多少字」**。
用户填 600 秒 + 10000 字，规划出 120 镜；W3 警告只说「实际时长与目标有差异」，不说「你内容不够」。

**规格**：
1. 规划期新增**内容密度判据**：由 `targetDurationSec` × 语速档（normal 8 / argument 10 / tender 5）推出**所需台词字数区间**；
2. 剧本字数显著低于下限 ⇒ 规划期**明确警告**「按目标时长 X 秒估算需约 N 字台词，当前剧本 M 字，成片将以静场/动作镜填充」；
3. 剧本字数超出下限 3× ⇒ 警告「台词密度过高，镜长可能装不下，将触发拆镜」。

**落点**：`auto-plan.js`（`planAutoShots` 尾部 warnings 汇总处 `:372-404`）+ `shot-duration.js` 的 `ZH_CHARS_PER_SECOND` 导出（`:388` 已在导出列表）。

**验收判据**：
- 规划 1800 秒 + 3000 字剧本 ⇒ 产出一条明确含「所需台词字数」与「当前字数」的 warning；
- 规划 1800 秒 + 36000 字剧本 ⇒ 产出密度过高 warning；
- 两类 warning 均可在 `FilmAutoPanel.vue:340-345` 的警告区渲染出（`plan.warnings` 已有渲染位）。

> ⇒ 连带效果：**M0′.3（出片消费逐镜 `durationSec`）解锁**（档 1 成立 ⇒ 逐镜时长可被消费）。

**现状（三重断裂）**：
1. `auto-plan.js:267-279` 逐镜算了 `resolveShotDurationMs`（formula 按引号内台词字数 / 档位兜底），
   产出 `durationMs / durationSec / durationSource`（`:309-311`）；
2. **但出片不消费它**：`auto-runner.js:163` 与 `:231` 都用 `seconds: Number(shot.seconds) || Number(project.seconds) || 5`，
   而 `shot.seconds` 是全局值（`auto-plan.js:308`）⇒ **逐镜时长是死数据**；
3. 溢出只警告不阻断：`auto-plan.js:344-365` 的 W9 汇总 overflow / truncated，**没有 fail-closed**。

**⚠ 实测证据（当前 10 分钟模式下即可复现，不是长篇化才有的问题）**：
用真实 `planAutoShots` + 真实随包 kit 跑「单段台词 + 用户选 5 秒档」：

| 台词字数（可发音单位） | 台词需时（8 字/秒） | 推算档位 | **实际出片镜长** | 逐镜警告 | plan 级警告 |
|---|---|---|---|---|---|
| 40 字 | 5.00s | 5s | 5s | 无 | W3 / W4 |
| **70 字** | **8.75s** | **10s** | **5s** | **无** | W3 / W4 / **W8** |
| **100 字** | **12.50s** | **12s** | **5s** | W9：「推算时长 12.5s 超过单镜上限 12s，必须按 long_dialogue_split 拆解台词，**不得截断**」 | W3 / W4 / W8 / **W9** |
| 130 字 | 16.25s | 12s（overflow） | 5s | 同上 | 同上 |

> 复现输入（**逐字**，供验收直接使用）：
> `script = 'INT. 街角 - 雨夜\n\n「' + <40|70|100|130 个可发音汉字> + '」'`，
> `characterRefs: []`、`sceneRefs: []`、`aspect: '16x9'`、`seconds: 5`、`targetDurationSec: 10`、`templateShots: <随包 kit 153 镜>`。
> ⚠️ 样本必须是**足长**的连续汉字（不是 `slice` 越界后的短串）—— 否则几个用例会跑出同一个结果。

**三条读数**：
- **70 字那档连逐镜警告都没有** —— 台词需要 8.75 秒、实际只给 5 秒，系统完全静默；
- **100 字那档 W9 明说「不得截断」，但系统不拆、不阻断，照样出 5 秒的片** ⇒ **警告与执行脱节**；
- 推算档位（10s / 12s）**完全没有被消费**。

⇒ **R3 的第一优先级不是「为长篇化补能力」，而是「修一个今天就在让用户拿到念不完台词的成片的缺陷」。**
⇒ 这条应从 M1 之后的 M2 **前移**，与 M0 并行启动（见 §五 里程碑顺序修订）。

**规格（档 1：provider 镜长可控 —— F-2 判定为「可控」）**：
- R3.1 出片**必须**消费逐镜 `durationSec`，不再用全局 `shot.seconds`；
- R3.2 `durationSec` 吸附到 provider 帧数档（`video-gen.js:53-60` `pickFilmFrameCount`：≤5→121 帧、≤8→201、≤10→241、**12→289（2026-10-24 已修，M0′.5）**；`FILM_FRAME_RATE = 24`）；
- R3.3 **fail-closed 的基准必须是「用户实际所选档位」，不是全局档位上限**：
  - 判据改为 **`snapToTier(rawSec)` 的结果 > 用户所选的 `o.seconds`**（或等价地 `rawSec > 用户所选档位`）；
  - ⚠️ **现机制的缺陷**：`auto-plan.js:240` 的 `durationMaxSec = Math.max(...durationTiers)` = **12**（全局上限），
    而 `W9` 的 overflow 分支判 `rawSec > durationMaxSec` ⇒ **「用户选 5 秒档、台词需 8 秒」这个最常见的场景永远不触发**
    （70 字那行实测：推算 10s ≤ 12 ⇒ 不 overflow ⇒ 逐镜警告为空）。
  - ⇒ **实现上必须引入「相对用户所选档位」的判据**，而不是调大 `maxSec`；
- R3.4 台词截断（`rawSec * 1000 > durationMs + 1`）⇒ 在 R3.3 的新判据下**同样升级为 fail-closed**（不再只是告警）；
- R3.5 R3.3/R3.4 的告警文案必须给出**用户可执行的两个出口**：「改大单镜秒数（到 N 秒）」/「把这段台词拆成两句」。

**规格（档 2：provider 镜长不可控 —— F-2 判定为「全不可控」）**（**⚠️ 本次不启用** —— 实测为全档可控）：

- R3.2′ **主动拆镜**成为强制策略：一段台词若超过「实测镜长 × 语速」能装下的字数 ⇒ **在规划期就切成多个镜**（`expandBeatsToCount` 扩展为「按台词容量拆」而非「按句末标点拆」）；
- R3.3′ 提示词内显式约束「本镜台词必须完整念出，不得加快语速」；

**规格（档 3：provider 镜长部分可控 —— F-2 判定为「部分可控」）**（**⚠️ 本次不启用** —— 实测为全档可控）：

- R3.1″ **逐档建表**：F-2 的逐档对照表就是本档的输入 —— 每一档（5/8/10/12 秒）标「可控 / 被钳制」；

**落点**：

- `auto-plan.js:267-311`（产出侧：档 2 需要扩展 `expandBeatsToCount`）

### R4 提示词契约：结构化台词块 + 冲突块处置

**现状**：
- 提示词 = `head`（场景头 + 你的剧情行）+ `characterLines`（模板的 `[CHARACTER: X]` 槽位行）+ **5 类白名单块**（`script-adapt.js:65-120`）；
- **没有结构化台词**：「谁说了什么」只以裸文本形式出现在 `head` 里；
- **模板内容几乎不参与**（§2.4 实测：保留率中位 0.10%，82% 的模板产出 ≤200 字符）——
  ⇒ `EXACT …` 硬约束**其实已被丢弃**（不匹配任何白名单模式），原片世界观**不会**被塞进用户剧；
  ⇒ 但反过来说，**影视工程方法论也没接上**：用户得到的是「自己的文案被原样送进模型」；
- **16% 模板的 `AUDIO` 块被归为静态类、从 videoPrompt 剔除**（`script-adapt.js:101`）—— 在 C3 前提下这是**反向优化**；
- 模板是**参考片的**：153 镜全是同一部片（4 个角色、95 分钟），且 `characterLines` 里的**槽位名仍是原片角色名**（`ROKO/JAXX/LULU/REIN`）。

**规格**：
1. **结构化台词块**：每镜提示词追加一个显式块，把该镜台词解析成「角色 + 台词 + 情绪」结构，供视频模型识别发声者与情绪。
   ```
   [DIALOGUE]
   小强:「你到底要走到哪一步？」
   ```
   - 角色名取自 `characterMap`（用户标注优先，见 R5.2）；
   - 台词来源：剧本中成对引号内文本（`shot-duration.js:98-110` `extractDialogueText` 已实现该抽取）；
   - 无引号 ⇒ 块内写明「本镜无台词」并触发 R2 的密度警告。
2. **`AUDIO` 块在自动模式下不再剔除**：C3 前提下音频语义是视频模型需要的输入。
   ⇒ 调整 `buildMotionPrompt` 的分类，或在自动模式专用的派生函数里把 `AUDIO` 块并入 motion 集。
   ⚠️ **注意**：这是对既有「三分提示词」契约的**局部例外**，必须只作用于自动模式，不改 `buildMotionPrompt` 的既有语义（画布/工程案例路径依赖它），否则会产生静默回归。
3. **（已撤销）角色槽位名替换**：初稿曾要求「把模板 `characterLines` 里的原片角色名替换为用户角色名」——
   **该前提经实测不成立**：随包 kit 里 `[CHARACTER:` 出现 **0 次**，`characterLines` 恒空 ⇒ **原片角色槽位名根本不在提示词里**，无对象可替换。
   ⇒ 本条**撤销**，但**保留一个前置检查**：若将来导入的 kit 带有 `[CHARACTER:]` 标记（`kit-import` 支持的旧版 kit 可能有），
   则该条**重新生效** ⇒ 落点：`kit-loader.js` 的导入校验处加一条「含 `[CHARACTER:` 的 kit 需在自动模式下替换槽位名」的显式提示。
   ⇒ 真正会把原片专有名词带进提示词的是**模板正文里的角色描述**（实测 77 个模板正文含 `EXACT`，含大量原片专名）—— 见 R4.6。
4. **模板正文专有名词的处置**（这才是「原片内容污染」的真实入口）：
   随包 kit 里 **77/153 个模板的正文含 `EXACT` 类硬约束**（含大量原片专名，如角色名、外貌描述），
   好在这些块**当前全部被丢弃**（§2.4 实测）⇒ **今天没有污染**；
   ⚠️ **但一旦 R4.5 决定「把方法论真正接进提示词」，这些块就会重新进入** ⇒
   **必须先决定「哪些块可接、哪些块带原片专名必须剥离」**，否则 R4.5 会把今天的「无污染」变成「有污染」。
   ⇒ 落点：`auto-prompt-dialogue.js`（新增）里做**白名单式的块接入**（只接 `GEO/ACTION TIMING/CHARACTER ACTING`，
   `AUDIO` 另议，`EXACT` 与含专名的块一律不接）。
5. **方法论接入的真实口径**（面板侧）：`buildMethodologySummary`（`film-engineering-auto-projection.js:26-62`）统计的是
   `promptVars` 的**变量填充率**（`totalVars: 7` / `hitVars`），而 `promptVars` 服务的是**任务模板渲染**路径，
   **与实际送进视频模型的 `prompt` 是两条不同的拼装路径**。
   ⇒ 面板当前的「方法论接入率」**不能**被读成「提示词里有多少影视工程语义」。
   ⇒ 必须二选一：① 把模板语义真正接进 `prompt`（R4.6）；② 面板把两个口径分开显示（且文案要说清测的是什么）。
6. **R4.6 的实现约束**：接入必须是**白名单式**（见 R4.4），不能简单地把 `allParts` 全量放行 ——
   否则 77 个含原片专名的 `EXACT` 类块会一并进入。

**落点**：
- 新增 `apps/desktop/electron/services/film-engineering/auto-prompt-dialogue.js`（新文件，**不要塞进 `script-adapt.js`** —— 该文件已在门禁点名清单边缘）
- `auto-plan.js:248-316`（shots 映射处派生 dialogue 块）
- `script-adapt.js:100-104`（AUDIO 块分类调整，仅限自动模式入口）
- `script-adapt.js:80-89`（`characterLines` 的角色名替换，仅限自动模式入口）
- `ipc-handlers/film-engineering-auto-projection.js:26-62`（面板口径）

**验收判据**：
- 规划一份含两角色对话的剧本 ⇒ 每镜提示词含 `[DIALOGUE]` 块，且角色名与 `characterMap` 一致；

**现状**：

4. **三态告警，不静默丢**：

   - 角色数 > 参考图上限（8）⇒ **明确告警「这些角色有名字但没有参考图」**（中间态，不是丢弃）；

**现状**：

**规格**：
1. **接 governor**（照抄 story2video 的做法，`story2video-stages.js:1071-1073`）：
   - `auto-runner.js` 的 `gen(...)` 调用包一层 `withModelBudget({ governor, type:'video', providerId, model }, …)`；
   - `governor` 从 `container.setup.js:144` 的 `apiUsageGovernor` 注入 IPC 依赖（**当前 `film-engineering-auto.js` 的 `deps` 里没有 governor，要新增**）。
2. **传 `providerRunContext`**：`auto-runner.js:158-171` 补传，使 `PROVIDER_CIRCUIT_OPEN` / 配额熔断生效。
3. **补单价表**：`adapters/_base/base.js:120` 的 `estimateCost()` 从恒 `null` 改为按 provider 查表（无表的 provider 显示「未知」而不是「0」）。
4. **确认卡显示金额**：规划期估算「镜数 × 单价」= 预计成本，与现有 `estimates`（`auto-plan.js:426-432`）并列展示。
   ⚠️ 上游 spec 明确说「清单式而非金额报价」⇒ **这是一次对上游决策的修订，必须在 spec 里显式改写，不能默默加字段**。
5. **任务级算力闸**：`auto-start` 准入时校验「本次预计消耗 ≤ 用户当前可用额度」；超限返回明确错误码（如 `AUTO_BUDGET_EXCEEDED`），并给出「缩短时长 / 改用更便宜的 provider / 分批」三个出口。
6. **零扣费点必须变成有扣费点**：接入会员积分计费（仅「生成」扣积分，「操作」不扣 —— 沿用既有计费边界）。
7. ⭐ **「队列排空感知」的熔断闸**（**2026-10-25 实测追加，见 §3.2.4 ②**）：
   - 依据：该 provider 的视频提交**近似互斥受理**，而**客户端超时 ≠ 服务端停止**
     ⇒ 一次超时留下的请求会**继续占着受理通道**（实测 102 条滞留 ⇒ 需约 45 分钟排空）
     ⇒ **固定间隔重投只会加长队列**（实测退火 120 秒后仍零成功）；
   - 规格：**连续出现「客户端超时」（当前上限 120s）⇒ 判定 provider 饱和 ⇒ 打开熔断**，
     在**队列排空估计时间**（`滞留请求数 × 成功请求平均耗时`）内**不再向该 provider 派发**，
     并把「预计恢复时间」暴露给面板；
   - ⛔ **禁止**用固定常数退避（实测 90–120 秒不足）；退避时长必须由队列长度推导。
8. ⭐ **视频 provider 的有效并发 = 1**（**2026-10-25 实测追加，见 §3.2.4 ①**）：
   - 依据：provider 近似串行受理，而 `PRODUCTION_BATCH_CONCURRENCY = 2`（`production-runner.js:14`，硬编码）
     ⇒ 第二个请求在队列里等满 120 秒 ⇒ 该镜判 failed；
   - 规格：批内并发对**视频 provider** 降为 **1**（或把视频提交客户端超时提到覆盖排队窗口，如 600s），
     且**限流与重试的前提一律按「有效并发 = 1」书写**；
   - ⚠️ **降并发本身不够**（它只是不再往队列里多投一个请求）⇒ 必须与第 7 条的熔断闸**同时**落地，
     否则在串行 provider 上照样雪崩。

**落点**：

- `ipc-handlers/film-engineering-auto.js:74-84`（deps 注入 governor）、`:266-426`（准入判据）

### R9 可靠性：有界重试

**现状**：
- `auto-runner.js:146-175`：每镜**恰好一次** `gen()`，失败即 `report(i,'failed',reason)`，**无 retry**；
- `production-driver.js:300-334`：批级 try/catch，失败批标 failed 继续下一批，**无批级重试**；
- 对照组：story2video 有 `withAssetTransientRetry(fn, {maxAttempts=3, rateLimitMaxAttempts=4})`（`story2video-stages.js:1481`）—— **自动模式无此物**。

**规格**：
1. 单镜级有界重试：瞬时错误（超时/网络/5xx）最多 3 次、指数退避；429 最多 4 次、遵守 `Retry-After`。
   ⇒ 直接复用 `story2video-stages.js:1481` 的 `withAssetTransientRetry`，**不要新写一套**。
2. 错误分类用 `adapters/_base/provider-error.js` 的 `classifyProviderFailure`（与 governor 同源）。
3. 重试计数必须**如实上报**（`onShotProgress` 的 reason 里带 `第 N 次重试`），让面板能显示「正在重试」而不是长时间无反馈。
4. 批级：批内全部镜失败 ⇒ 批标 failed 但**不阻断后续批**（保持现状），并在收口时点名缺镜。
5. ⭐ **「单次调用向 provider 投出的请求数」必须设上限**（**2026-10-25 实测追加，见 §3.2.4 ②**）：
   - 依据：适配器内部已有 **6 次尝试**（退避 20/30/45/60/60 秒），上层若再叠加重试
     ⇒ **单镜最多投出 78 个请求** ⇒ 在串行 provider 上等于**请求洪水**（实测触发雪崩）；
   - 规格：**端到端（适配器内部 + 上层）**的尝试次数有**单一上限**，
     且该上限**不得**由「适配器 × 上层」相乘得到 ⇒ 需在某一层收口；
6. ⭐ **客户端超时后不得立即重投同一请求**（**2026-10-25 实测追加，见 §3.2.4 ②**）：
   - 依据：客户端超时后**服务端很可能仍在生成** ⇒ 立即重投 = 往已饱和的队列再加一个请求；
   - 规格：超时类失败的重试间隔必须 **≥ 队列排空估计时间**（与 R8 第 7 条同一读数），
     **不得**用固定常数；且重试计数要能区分「客户端超时」与「业务失败」（前者进饱和判定）。

**落点**：
- `auto-runner.js:146-175`（重试包裹）
- `story2video-stages.js:1481`（**复用源**，只读不改）

**验收判据**：
- 注入一个前 2 次失败第 3 次成功的桩 ⇒ 断言该镜最终 `status === 'done'`，且 provider 被调用 3 次；
- 注入一个恒定失败的桩 ⇒ 断言调用次数 == 3（不是无限），且 `error` 文案含「重试 3 次仍失败」。

### 5.1.2 精确判据（数据校验）

> 判据：**`rawSec > 用户所选档位 + 吸附容差(0.3s)`**
> 其中 `rawSec` = 按语速推算的台词需时（`ZH_CHARS_PER_SECOND.normal = 8 字/秒`，情绪档 `argument=10` / `tender=5`），
> 「用户所选档位」= 用户在面板上选的**单镜秒数**（`o.seconds`，取值 5 / 8 / 10）。

⚠️ **为什么不能用 `snapToTier(rawSec) > 用户所选档位`**：
吸附会把溢出值吸到**最大档**（`DEFAULT_TIERS = [5,8,10,12]`）⇒
「用户选 10 秒 + 台词需 12.5 秒」会被吸成 12 秒 ⇒ `12 > 10` 成立但 `12 > 12` 不成立
⇒ 若拿吸附后的值比，**这一格永远漏判**。

⚠️ **为什么不能用现状的 truncation 判据（`rawSec*1000 > durationMs + 1`）**：
它拿**吸附后**的档位比 ⇒ 「用户选 8 秒、内容 5.125 秒被吸附到 5 秒」会被判成「截断」
⇒ 实测在改动前就会误报 W9（`41 字 + 8 秒档` 也会出 W9）⇒ **与「用户选了 8 秒」的意图直接矛盾**。

⚠️ **为什么容差取 0.3s**：
`snapToTier` 明确接受「内容比档位多 `toleranceSec` 以内」（否则「40 字→5s、41 字→8s」会出现 +60% 的跳变）。
若容量判定不认这个容差 ⇒ 「41 字（5.125s）在 5 秒档」会被拦，而**吸附本身却当它合法**
⇒ **判据与实现自相矛盾** ⇒ 两者必须同容差。

### 5.1.4 功能逻辑（流程）

```
规划（planAutoShots）
  │
  ├─ ① 输入校验（validateAutoInputs）：剧本非空 / 字数上限 / 画幅 / 单镜秒数 / 目标时长 / 参考图
  │
  ├─ ② 分场（splitAutoBeats）→ 拆句（expandBeatsToCount）→ 并段（mergeBeatsToCount）
  │      └─ 拆句时把「切分碎片」并回前一块（M0′.4 修复：末尾孤立 `」` 曾让整段判为不可拆）
  │
  ├─ ③ 逐镜推算时长（resolveShotDurationMs）
  │      ├─ 容量基准 capacitySec = 用户所选单镜秒数（缺省 = 物理上限 12s）
  │      ├─ 产出 durationMs / durationSec / durationSource / durationRawSec
  │      └─ 产出 capacityOverflow = (rawSec > capacitySec + 0.3s)
  │
  ├─ ④ 容量不足的镜 → 追加**逐镜出口文案**（两个出口）
  │
  ├─ ⑤ 汇总告警（W2 批数 / W3 时长差 / W4 无角色 / W5 墙钟 / W6 参考图 / W7 空镜 / W8 推算差 / W9 容量 / W10 少产）
  │
  ├─ ⑥ W10：目标镜数 > 实际镜数 → 报告少产镜数 + 成因 + 出口（**不阻断**）
  │
  └─ ⑦ 容量不足 ⇒ **fail-closed**：返回 { ok:false, errorCode:'AUTO_DIALOGUE_OVERFLOW', message, shots, warnings }
```

⚠️ **为什么容量不足要阻断，而少产镜数只报告**：
- 容量不足 ⇒ **产出的成片一定念不完** ⇒ 用户拿到的是坏结果（还要等 15 小时才发现）⇒ 必须在 1 秒内拦下；
- 少产镜数 ⇒ 产出的成片**能念完**（只是比目标短）⇒ 不是坏结果 ⇒ 报告即可，不该让整个规划失败。

### 5.1.8 本次修掉的两个 PRD 未记的缺陷（实测发现）

| # | 缺陷 | 现象 | 修法 |
|---|---|---|---|
| **①** | **切分碎片让整段判为不可拆** | `expandBeatsToCount` 的可拆判据是 `chunks.every(c => c.length >= 2)`；而切块正则会把末尾的 `」` 切成**独立的一块**（长度 1）⇒ **整段判为不可拆**。实测：`「他站在雨里。他把信塞进信封。他转身离开。」` 目标 4 镜**只出 1 镜** —— 用户明明写了句号却拆不开 | `auto-beat-splitter.js` 的 `splitIntoChunks` 把碎片**并回前一块**（保序、不丢字） |
| **②** | **12 秒档的帧数映射错了** | `pickFilmFrameCount` 的旧表 `d > 10 → 441`；**441 是适配器上限**（8n+1 且 ≤441），不是 12 秒的映射 ⇒ 441 帧 @24fps = **18.375 秒**（比目标长 53%）。⚠️ **当前生产链路上 441 帧还不可达**（`video-gen.js` 的 `FILM_DURATIONS = [5,8,10]` + 提交前硬校验，且出片用的是**全局** `shot.seconds`）⇒ 这条是**为 M0′.3（出片消费逐镜 `durationSec`）铺路的潜在正确性修复**：一旦出片改为消费逐镜推算值，推算层会吸附到 12 秒档 ⇒ 提交 441 帧 ⇒ 成片超时 53%。 | 12 秒档 ⇒ **289 帧**（12s × 24fps = 288，取 8n+1 ⇒ 289 ⇒ 12.0417 秒） |

⚠️ **顺带订正 PRD §四 R3 的两处口径**（本次以实测为准）：
1. **§四 R3 的验收判据**写「70 字 + 5 秒档**必须产出逐镜警告**」，而 §五 M0′.2 写「70 字 + 5 秒档 ⇒ **规划失败**」
   ⇒ 两处不一致 ⇒ **以 M0′.2 为准**（更严、且产品上正确：警告与执行脱节本身就是缺陷）。
   逐镜警告**并未消失** —— 它随 fail-closed 的返回体（`shots[].durationWarnings`）一起带出。
2. **「12 秒档在自动模式不可达」不准确**：`DEFAULT_TIERS = [5,8,10,12]` 含 12 秒 ⇒
   **用户选不了 12 秒**（输入白名单只有 5/8/10），但**推算会吸附到 12 秒** ⇒ 该档位在自动模式下**可达**。
